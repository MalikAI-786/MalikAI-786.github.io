# Brand design

## Canonical identity
Use the existing Reference Mark system and repository tokens/assets as the source of truth. Do not redesign the brand per task.

Core defaults:
- Ember as the primary accent.
- Warm graphite / paper surfaces.
- Verdigris as the secondary analytical/accent hue where already defined.
- Existing logo/mark assets from `assets/brand/`.
- Existing typography hierarchy and token files rather than hard-coded lookalikes.

## Required method
1. Inspect `assets/brand/tokens.css`, `assets/brand/palette.py`, and relevant existing artifact before designing.
2. Reuse the correct logo lockup/mark at an appropriate scale; do not distort, recolor arbitrarily or create faux variants.
3. Keep one visual hierarchy: statement/headline, body, instrument/data labels.
4. Prefer restrained, information-dense layouts over decorative clutter.
5. Maintain WCAG-conscious contrast, readable type sizes and mobile behavior.
6. For professional artifacts, branding should signal ownership without overpowering the content.
7. For email, legal, resume and research artifacts, use the relevant domain skill too; brand rules never override domain conventions.

## Cross-format rule
The same identity should be recognizable across GitHub Pages, resumes, PDFs, slides, email signatures and social assets. Reuse tokens and marks; adapt spacing and composition to the medium.

## Quality gate
- Existing tokens/assets were used.
- Logo is present only where appropriate and rendered cleanly.
- Palette matches canonical tokens.
- Information hierarchy is obvious in five seconds.
- No private data was embedded into public design assets.
